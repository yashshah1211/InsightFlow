## Official demo on Vercel

1. Review permission to distribute the competition dataset. Place the unchanged original at `data/raw/customer_feedback.csv`, then run `npm ci`, `npm run data:inspect`, `npm run data:prepare`. Source SHA-256: `82b09450e0e5144c4a21cb33a9556dab6afd7618228496e7f4c321f687250c41`. The generated JSON is about 5.7 MB; raw data and generated outputs stay outside Git.
2. Use repository root, Next.js framework, Node 22+ (tested on Node 24), build command `npm run build`. Set `INSIGHTFLOW_DATA_MODE=official` for Production and intended Preview environments; keep `INSIGHTFLOW_WRITES_ENABLED=false` initially. Explicit official mode fails the build if the artifact is missing.
3. For an authorized CLI deployment, prepare the artifact locally before uploading. `.vercelignore` excludes raw CSV, secrets, pilots and worktrees, and allows the generated JSON; Next API traces include it. For Git-based builds, supply an approved private build input or explicitly approve artifact redistribution. A Git push alone does not supply ignored data. No automatic remote data fetch is configured; do not embed signed download URLs or tokens.
4. Put environment values in Vercel settings with appropriate Production/Preview scope, then redeploy when changing them. Never expose service-role or Adaption keys with `NEXT_PUBLIC_`. Neither is needed for public reads. [Vercel environment documentation](https://vercel.com/docs/environment-variables).
5. After separate deployment authorization, run both smoke scripts with `SMOKE_BASE_URL` pointing to the deployment. Verify six pages, official provenance, 7,000/320/6,680 counts, CSV download and print. Locally, `npm start -- --port 3100 --hostname 127.0.0.1` runs the standalone package; stop it before rebuilding on Windows.

## Enable private Supabase persistence

1. Choose your project and Auth provider. Configure Site URL, exact local/production redirect allowlist, email delivery or OAuth settings. If choosing anonymous sign-in, deliberately enable it and configure abuse limits/CAPTCHA. Use two separate test users. No service/project was created by this task.
2. With separately authorized migration-admin access, review/apply `202610110001_foundation.sql`, then `202610110002_authenticated_rpcs.sql` from `supabase/migrations`. RLS scopes reads; owner-derived RPCs scope atomic writes. Direct table writes and anonymous RPC execution remain revoked.
3. Set server `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` (or legacy `SUPABASE_ANON_KEY`) and exact `APP_ORIGIN`. Enable `INSIGHTFLOW_WRITES_ENABLED=true` only after Auth/migration checks pass. Default official reads can remain active; UUID `batchId` selects private storage. Application handlers do not use `SUPABASE_SERVICE_ROLE_KEY`.
4. **Remaining UI prerequisite:** add cookie-aware sign-in with installed `@supabase/ssr` `createBrowserClient` and the selected Auth method. Browser configuration may intentionally expose public `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`; the current UI does not consume them. OAuth requires a PKCE callback to exchange the code and set cookies. A local-storage token alone does not establish the server session. Server `getUser` verifies identity; API proxy refreshes cookies with `getClaims`. [Current Supabase SSR guide](https://supabase.com/docs/guides/auth/server-side/creating-a-client?queryGroups=framework&framework=nextjs).
5. **Remaining UI prerequisite:** select returned private `meta.batchId` for all reads, exports and evidence links after add/import. The current UI explores the public demo and has no sign-in flow/private batch selector. Credentials alone do not complete the persistent end-to-end UI workflow; cookie-authenticated API tests can run first.
6. Live test: POST manual feedback, read its returned batch, import CSV, retry identical bytes (same batch/`idempotentReplay=true`), inspect evidence, PATCH status/notes, POST action, then reload to prove persistence. Missing `observedAt` stays null. Invalid semantic rows report rejects; malformed/oversize imports fail atomically.
7. Negative tests: unsigned/expired/forged cookies -> 401; foreign Origin -> 403; user B reading/mutating user A's batch/issues -> 404; authenticated demo mutation -> 403. Direct table/anonymous RPC writes must fail. Local Auth mocks plus real PGlite transactions do not prove remote Auth/RLS deployment.

## One real Adaption pilot: prerequisites only

1. Run offline `npm run adaption:prepare`. Review the 25-pattern `pilot.csv`, blank `human-review.csv`, `config.json`, `manifest.json` under ignored `artifacts/adaption`. Source/config/pilot hashes bind inputs; dataset/run IDs and estimated/actual credits are null.
2. Obtain account access, data-transfer permission and an API key from Adaption Settings. Keep `ADAPTION_API_KEY` in the local environment/secret manager. Account balance and pilot cost are **unknown until an actual provider quote**; no numerical estimate was obtained.
3. Use Python 3.11+ in a virtualenv and `python -m pip install -r scripts/adaption/requirements-optional.txt` for inspected `adaption==0.14.0`. Offline preparation/tests need no SDK installation. Recheck signatures/config before any SDK upgrade.
4. After explicit transfer authorization, upload **only the reviewed pilot** using the provider app or a separately reviewed uploader, capture its real dataset ID and confirm 25 imported rows. No automatic uploader is implemented. Prompt/context column mapping is in config; missing-completion generation is described in the [app walkthrough](https://docs.adaptionlabs.ai/tutorials/adaptive-data-app-walkthrough/). Actual exported columns/correspondence still need inspection.
5. With separate quote/network authorization, run `npm run adaption:estimate -- --dataset-id ACTUAL_DATASET_ID --allow-network`. It uses `estimate=True`, manifest-bound config and disabled retries. The [current quickstart](https://docs.adaptionlabs.ai/adaptive-data-quickstart) describes a quote without starting a run. Review the actual credits/config hashes before approving spend.
6. Paid execution remains disabled. A separately reviewed one-run runner/download mapper must be implemented **after explicit approval of the visible quote**. No unattended retries. Record actual IDs, status, SDK/config/output versions, source/config/artifact hashes, costs when available and sanitized errors. No provider output exists locally.
7. Independently verify gold sentiment, issue topics and severity before spending. After an approved run, map real output to canonical JSONL (`normalizedHash`, `annotation`) and real `RunProvenance`; run `npm run adaption:validate -- --input ACTUAL_NORMALIZED_JSONL --provenance ACTUAL_PROVENANCE_JSON`. Check 25 hashes, exact quotes, denied-fraud safety, null confidence, unreviewed provider labels and provenance hashes. Compare provider output with the heuristic baseline on the same human-labeled patterns; disclose rejected/missing coverage. The validator computes sentiment accuracy only; topic/severity evaluation and unbiased paired comparison need review. Schema validity does not prove accuracy or improvement.
8. Store only reviewed actual run provenance with authorized administrator access; no public RPC creates runs. Data Lab reads stored runs and nullable usage without auto-activating annotations or claiming account balance.
