# Architecture — Phase 1 baseline and Phase 2 extension

Release note, 2026-10-12: the current six-screen HTTPS app has real cookie Auth,
owner-scoped persistence and 32 hosted acceptance checks. One real Adaption synthetic pilot completed; 25 returned candidates passed
structural/evidence checks and zero are human-approved. Static aggregate proof
is prepared in Data Lab separately from batch analytics; no classifier is trained. See the
[submission architecture](SUBMISSION_ARCHITECTURE.md) and
[current Adaption status](ADAPTION_SUBMISSION_STATUS.md). The phase notes below
are historical snapshots; their pending/no-deployment statements are not current.

Current Phase 5B extension: Phase 5A is integrated by verified fast-forward; password UI and all six screens share server-discovered private selection. GET /api/batches uses additive batches-1.0.0, verified owner filtering and existing workspace RLS. HTTP-only cookies, reauthorized ID-only restore, keyed state cleanup and truthful sign-out failures close auth/cache gaps. No domain contract/migration/dependency versions changed. See PHASE5B_HANDOFF.md and BATCH_API_CONTRACT.md for current behavior.

Current Phase 4 extension: production mode is explicit and official builds/runtime share full artifact + original-row fingerprint validation; isolated package HTTP verification retrieves the complete dataset. Server `/api/auth` password sign-in/out, verified-session and PKCE callback routes complete cookie plumbing without UI edits. Domain v1.0.0 is unchanged; additive auth-1.0.0 schemas are separate. Existing owner-derived RPCs/RLS remain unchanged and unapplied remotely. Adaption now has separately hash-gated provider commands and a local human-approved training-curation/paired evaluation workflow; no provider call was made. See PRODUCTION_PACKAGING.md, SUPABASE_PRODUCTION_GUIDE.md, AUTH_UI_HANDOFF.md and ADAPTION_PHASE4_WORKFLOW.md for current behavior; older phase sections below are historical.

Next.js App Router and TypeScript share one src-based repository. Route handlers validate input and response with Zod v1 contracts, call a server-only repository, and return explicit provenance. Pure analysis functions parse UTF-8 CSV, retain raw records, group by batch plus SHA-256 of normalized text, calculate coverage and rank explainable issues. No browser bundle receives database or Adaption credentials.

The deterministic repository returns 10 authored records and 9 exact text patterns. It implements FeedbackRepository.snapshot(batchId); unknown batches return 404. Every response labels fixture mode. INSIGHTFLOW_DATA_MODE defaults to fixture; selecting an unsupported database mode fails closed with 503 rather than quietly returning sample data. This is the seam for authenticated Supabase persistence in Phase 2. No Supabase SDK is installed until used.

Read-only endpoints cover dashboard, feedback records/patterns, issues/evidence, decisions, Data Lab and CSV summary export. Write paths return a typed 401 before reading bodies. Phase 2 must verify sessions, derive owner scope server-side, validate origin/CSRF, limit request streams before multipart decoding, apply file/parser checks, and perform an atomic import with idempotency. Content hash unique per workspace makes exact retry detection possible. Do not expose service-role writes to a caller-selected workspace.

SQL scopes all tables to workspaces. Composite foreign keys prevent evidence, feedback and actions from linking across workspaces. Anonymous/authenticated roles receive SELECT only under RLS for curated demo or caller-owned workspace. No write grant or policy exists. Migration-admin/service-role seeding is privileged and never shipped to clients. Demo workspaces have no owner and are read-only to all clients; private workspace owner IDs must agree with row owner IDs. Only explicitly reviewed sample data belongs in the demo workspace; raw private uploads must never be seeded there. Error/config JSON in adaption_runs must be sanitized before persistence because demo rows can be publicly read. Auth/session verification and server-owned write authorization are Phase 2 requirements.

At this phase no migration has been applied to a remote Supabase database. Migration checks run in an ephemeral Postgres-compatible engine with Supabase auth/role stubs; they do not replace a real deployment check. No actual customer records, live AI inference, Python network pilot, persistence, or end-to-end save workflow is claimed. UI consists only of navigation and handoff placeholders.

Scale assumptions: 5 MiB per CSV, 50,000 logical data rows, 10,000 characters per review, page sizes 1–100; intended hackathon single-user/demo traffic. Rejected semantic rows are reported by logical CSV row number, malformed quoting aborts the import. SHA-256 groups preserve all category memberships and never deduplicate across batches. Only full successful transactions become ready. No time-series is inferred from ingest times.

Primary references: [Next.js installation](https://nextjs.org/docs/app/getting-started/installation), [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security). Dependency versions are pinned in package.json and lockfile; runtime baseline Node 22+ (verified locally on Node 24).

Phase 2 supersedes the baseline's fixture-only/no-SDK/write-stub statements: a generated artifact repository serves the verified official CSV without credentials; cookie-aware Supabase clients support private snapshots and atomic writes. src/proxy.ts refreshes API cookies; requireSession uses getUser before authorization. No service-role adapter is used. Authenticated SQL RPCs derive owner from auth.uid() and perform complete imports in a transaction, with owner workspace locking and content-hash retry detection. Direct table write grants remain revoked. Same-origin checks, 64 KiB JSON limits and 5 MiB CSV plus bounded multipart overhead apply before decoding. Public official/fixture issues cannot be changed by these write handlers. No remote Supabase deployment has occurred.

Frozen v1 fields are unchanged; the artifact uses existing mode=database and provenance.source=official_csv with an explicit label. Supported environment modes are fixture, official and database; private UUID batch selection can coexist with public default reads. Persisted issues retain UUID identity/status; rankings recompute from current distinct-pattern evidence. Raw import time never fills observedAt. Official artifact and Python pilot files are excluded from Git, included locally only as reviewed deployment inputs. See OFFICIAL_DATA.md for source proof and deployment tracing, SUPABASE_SETUP.md for auth/migrations, and ADAPTION_INTEGRATION.md for offline preparation and blocked paid execution.
